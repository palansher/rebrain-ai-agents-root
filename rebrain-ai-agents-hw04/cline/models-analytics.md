# Аналитика расхода токенов: Plan vs Act

Документ фиксирует фактический расход токенов при выполнении задания
(проект `news-monitor`, hw04) в двух режимах Cline — **Plan** и **Act** —
с разбивкой по моделям, и содержит вывод о том, оправдало ли себя
использование более дешёвой модели в Act Mode.

## 1. Источник данных

Cline сохраняет историю задачи в файл сессии:

```
~/.cline/data/sessions/<sessionId>/<sessionId>.messages.json
```

В этом файле для **каждого ответа ассистента** есть блок `metrics`:

```json
{
  "inputTokens": 6624,
  "outputTokens": 118,
  "cacheReadTokens": 0,
  "cacheWriteTokens": 0
}
```

и блок `modelInfo`:

```json
{ "id": "deepseek-v4.1-flash", "provider": "opencode-go" }
```

Режим, в котором был сделан запрос, определяется по атрибуту `mode` в теге
пользовательского сообщения: `<user_input mode="plan">` / `<user_input mode="act">`.
Ассистентские сообщения, идущие после сообщения пользователя, относятся к его режиму.

Проверено, что в UI Cline (Account → Usage History) показывается только дата,
модель и списанные кредиты (у ClinePass-модели — `$0.0000`), **без токенов**;
метрики токенов доступны только в файле сессии.

Снимок данных на момент анализа: **238 запросов** (51 в plan + 187 в act),
сессия `1795058974405_sk103`. Файл сессии дописывается, поэтому при повторном
запуске скрипта числа немного вырастут.

## 2. Методика

- `inputTokens` — весь вход запроса, **включая** токены, прочитанные из кэша.
- `cacheReadTokens` — подмножество `inputTokens`, прочитанное из кэша.
- **Некэшированный input** = `inputTokens − cacheReadTokens` — то, что
  тарифицируется по полной цене.
- `outputTokens` — сгенерированные токены (ответы + tool-вызовы).
- ⌀ значения — средние на один запрос (одно обращение к модели).

## 4. Расход по режим × модель

| Режим | Модель (provider/id) | Запросов | Input | ⌀ input | Output | ⌀ output | Cache read | Cache % | Некэш. input | ⌀ некэш. |
|---|---|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| act | `cline-pass/cline-free/nemotron-3.5-super-vl` | 137 | 12 960 630 | 94 603 | 44 823 | 327 | 11 997 712 | 92.6% | 962 918 | 7 029 |
| act | `opencode-go/deepseek-v4.1-flash` | 50 | 11 895 846 | 237 917 | 19 894 | 398 | 11 348 992 | 95.4% | 546 854 | 10 937 |
| plan | `opencode-go/deepseek-v4.1-flash` | 51 | 5 004 688 | 98 131 | 23 093 | 453 | 4 578 304 | 91.5% | 426 384 | 8 360 |

Роли моделей: `nemotron-3.5-super-vl` — **бесплатная** (ClinePass, `$0.0000`),
`deepseek-v4.1-flash` — **платная** (opencode-go), то есть более дорогая.
В Act Mode начали на бесплатной nemotron; после исчерпания дневного лимита работа
продолжилась на платной deepseek. В Plan Mode использовалась платная deepseek.

## 5. Выводы

1. **Plan «плотнее» на шаг.** 51 запрос против 187 в act (act — в 3.7 раза больше
   обращений), но output на шаг у plan выше: 453 против 346. План — это небольшое
   число насыщенных шагов.
2. **Act дороже в абсолюте из-за числа шагов, а не из-за размера шага.**
   24.9M input против 5.0M — следствие tool-loop: каждый tool-вызов — новый запрос
   с полным контекстом.
3. **Кэш промпта работает отлично в обоих режимах:** 91.5% (plan) и 93.9% (act),
   у deepseek в act — 95.4%. Рост контекста почти не оплачивается по полной цене.
4. **Нормированные метрики режимов близки:** ⌀ некэшированный input 8 360 (plan)
   vs 8 074 (act); ⌀ output 453 vs 346. «Цена шага» в plan выше по выходу,
   в act — по количеству шагов.
5. **По моделям внутри act:** бесплатная nemotron (ранние шаги) — самый экономный
   по свежим токенам (7 029/запрос); платная deepseek (поздние шаги) — 10 937/запрос,
   но у неё выше доля кэша (95.4%) и длиннее ответы (398 vs 327). Это объясняется
   характером поздних шагов (написание README/аналитики, финальные прогоны), а не
   «болтливостью» модели.
6. **Стоимость.** Тарифов провайдера в данных нет, поэтому считать надо по формуле
   `cost = uncached_in·price_in + cache_read·price_cache + output·price_out`
   (цены — за 1M токенов). Nemotron в Act Mode стоила `$0`; для платной deepseek
   объёмы за 50 запросов: 546 854 некэш. input, 11 348 992 cache read, 19 894 output —
   при типичных тарифах лёгких моделей это единицы центов.

## 6. Оговорки

1. Данные — **снимок живой сессии**; при повторном запуске скрипта числа изменятся.
2. `inputTokens` **включает** кэшированные токены, поэтому корректно сравнивать
   именно «некэшированный вход» (`input − cacheRead`).
3. Разделение по режимам опирается на атрибут `mode` в пользовательских сообщениях;
   сообщения `[TASK RESUMPTION]` наследуют предыдущий режим.
4. Сравнение nemotron vs deepseek в act **не является контролируемым A/B**: модели
   работали на разных этапах (nemotron — создание кода, docker-сборки, отладка;
   deepseek — финальные прогоны, README, аналитика) с разным объёмом контекста
   и разными типами операций.
5. Стоимость в $ не рассчитана: тарифы провайдера не входят в данные.

## 7. Оправдало ли себя использование более дешёвой модели в Act Mode?

**Да, оправдало** — дешёвая (бесплатная) модель выполнила основной объём работы
в Act Mode, а переход на платную был вызван исчерпанием лимита, а не недостатком
качества.

Как было фактически:

- В Act Mode **137 из 187 запросов (≈73%)** и почти весь объём работы выполнены на
  **бесплатной** `nemotron-3.5-super-vl`: шаги 1–5 — каркас проекта, docker-compose,
  monitor (RSS, публикация в Stream, дедупликация), worker (FastStream, asyncpg, NER),
  обработка ошибок и README.
- Остальные **50 запросов** (шаг 6: чистый прогон `down -v && up --build`, чек-лист,
  аналитика) выполнены на **платной** `deepseek-v4.1-flash` — только потому, что у
  nemotron закончился дневной лимит.
- В Plan Mode использовалась **платная** `deepseek-v4.1-flash`; на планирование ушло
  5.0M input и 23k output — это **≈17% входных и ≈26% выходных** токенов задачи.

Аргументы «за» (дешёвая модель в Act Mode):

- Бесплатная модель довела реализацию до рабочего состояния: после её шагов система
  собиралась, опрашивала 3 ленты, писала новости и сущности в PostgreSQL, проходила
  проверки ruff. То есть на 73% запросов режима Act дешёвой модели хватило.
- Нормированные метрики у nemotron лучше: ⌀ некэшированный вход 7 029 против 10 937
  у deepseek, ⌀ output 327 против 398 (deepseek на своих шагах больше писал файлов:
  README, аналитика, скрипт).
- Стоимость для бесплатной модели — буквально `$0.0000` (подтверждено Usage History
  в Cline), т.е. основной массив работы в Act Mode обошёлся бесплатно.

Аргументы «против» и ограничения:

- Переход на платную модель всё равно произошёл: бесплатный тариф ограничен дневным
  лимитом, и на длинной задаче (187 запросов в act) его не хватило. Это риск квоты,
  а не качества.
- 187 запросов в act против 51 в plan — это природа режима (tool-loop), а не
  свойство модели; сравнивать «токены на задачу» между режимами некорректно,
  корректно — «токены на шаг» и «число шагов до результата».
- Строгого вывода «nemotron лучше/хуже deepseek» данные не дают: нет A/B на
  одинаковых подзадачах. Для такого вывода нужен контролируемый прогон одной и той
  же задачи на обеих моделях.

**Итог:** дешёвая модель в Act Mode себя оправдала — она выполнила основную часть
работы (73% запросов) без деградации результата, а платная понадобилась из-за
исчерпания бесплатного лимита, а не из-за ошибок или «нехватки ума». Планирование
на более дорогой модели обошлось в ≈17% входного бюджета задачи — для 51 запроса
это приемлемая цена за качественный проект.

## 8. Как воспроизвести

```bash
# последняя сессия Cline
uv run python scripts/token_stats.py

# конкретная сессия
uv run python scripts/token_stats.py --session ~/.cline/data/sessions/<id>/<id>.messages.json

# все сессии суммарно
uv run python scripts/token_stats.py --all-sessions

# машинно-читаемый вывод
uv run python scripts/token_stats.py --json
```

Скрипт `scripts/token_stats.py` использует только стандартную библиотеку,
не требует зависимостей проекта и работает с любым файлом сессии Cline.
